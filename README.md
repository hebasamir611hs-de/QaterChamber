# Automation Framework

Generated by `scaffold-automation-framework` (deterministic boilerplate via
`scaffold_generator.py`) — surface: **web**. See the plugin's
`automation-standards.md` for the full contract this framework implements.

## Setup

```
pip install -r requirements.txt
playwright install  # downloads browser binaries
```

## Configuration

All configuration lives in **one file: `.env` at the project root** — shared
with the QA Engine MCP server. There is deliberately no second env file:
`config/settings.py` loads it by absolute path derived from its own location,
so values resolve identically no matter which directory pytest, the locator
extractor, or `tools/save_auth.py` was invoked from.

Keys read by this framework (see the "Test automation framework" block in
`.env` for the full annotated list):

| Key | Meaning |
| --- | --- |
| `PROJECT_NAME` | Report/attachment naming |
| `ENV` | `dev` \| `staging` \| `uat` \| `prod` |
| `WEB_BASE_URL` | Site origin, no trailing slash or path |
| `ARABIC_PATH_PREFIX` | Language path prefix (`/ar`) |
| `CONTROL_PANEL_URL` | Liferay Control Panel base — control-panel tests only |
| `TEST_USER` / `TEST_PASSWORD` | Credentials for `tools/save_auth.py` |
| `AUTH_STATE_PATH` | storageState location, resolved against the project root |
| `VIEWPORT_WIDTH` / `VIEWPORT_HEIGHT` / `HEADLESS` | Browser defaults |

Page Objects must never hard-code a site URL. Build them from the base:

```python
from config.settings import web_url

HOME_URL = web_url("/home")                  # https://<base>/home
HOME_URL_AR = web_url("/home", locale="ar")  # https://<base>/ar/home
```

`web_url()` raises if `WEB_BASE_URL` is unset, so a broken `.env` fails at
collection with a clear message instead of silently navigating nowhere.
(`web/pages/example/example_page.py` is the one exception — it targets
`https://example.com` on purpose, to prove the stack with no project config.)

## Run

```
pytest                        # everything
pytest -m regression          # the critical re-run subset
pytest -m web                 # public-site cases only
pytest -m control_panel       # control-panel cases only
pytest --collect-only         # quick syntax/import check
pytest --no-clean-evidence    # keep previous runs' screenshots/videos/traces
```

`--alluredir` and `--clean-alluredir` already live in `pytest.ini`'s `addopts`,
so every run writes a fresh `reports/allure-results` — no flags to remember and
no results left over from the previous run. There are no `smoke` / `sanity`
markers — those were removed from the taxonomy; use `regression` plus the
platform marker(s).

## Reports

```
allure serve reports/allure-results                                   # interactive
allure generate reports/allure-results -o reports/allure-report --clean
python tools/clear_reports.py                                         # wipe everything under reports/
python tools/clear_reports.py --report --dry-run                      # preview one target
```

`reports/` holds two kinds of thing side by side:

| Path | What | Filenames |
|---|---|---|
| `reports/allure-results/` · `reports/allure-report/` | Allure's own data + generated site | GUID/hash — **Allure's format, not ours** |
| `reports/screenshots/` · `reports/videos/` · `reports/traces/` | every evidence file, archived for browsing | `<kind>_<date>_<time>_<TC-ID>_<PROJECT>.<ext>` |

The readable names exist because Allure never keeps them on disk: raw results
are `<guid>-attachment.png` and `allure generate` re-hashes those again into
`data/attachments/<hash>.png`. The archive folders are the browsable copy; the
Allure report keeps working untouched, showing the same readable name in its UI.

Evidence archives are cleared at session start alongside `--clean-alluredir`, so
`reports/` always reflects the current run. Pass `--no-clean-evidence` to
accumulate across runs instead. The clear step is skipped on `pytest-xdist`
workers, so a parallel run (`-n 3`) keeps every worker's evidence.

## Structure

The framework lives **at the project root** — there is no `automation/`
subfolder. `config/`, `core/`, `tools/`, and `web/` are top-level packages,
and `conftest.py` / `pytest.ini` sit beside them, so `pytest` run from the
repo root Just Works with no path argument.

- `config/` — `settings.py`: the single env-loading and URL-building module.
- `core/` — generic wrappers, never feature-specific.
- `web/pages/` · `mobile/screens/` — Page/Screen Objects, grouped per page/module.
- `web/tests/` · `mobile/tests/` — one test module per page/feature **per
  platform** (`test_<page>_<platform>.py`); all of a page's cases for one
  platform accumulate in that module — never one file per test case, and never
  two platforms in one file (they use different base URLs and are selected
  separately with `-m`).
- `tools/` — `extract_locators.py` (CLI-first locator harvest), `save_auth.py`,
  `clear_reports.py`.
- `reports/` — generated Allure results/report + readable-named evidence
  archives (git-ignored). See **Reports** above.
- `.claude/` — QA Engine project context; **not** part of the framework and
  pruned from pytest collection via `norecursedirs` in `pytest.ini`.

Root placement is now the standard: `automation-standards.md` and
`scaffold_generator.py` generate at the project root, so re-running
`scaffold-automation-framework` here fills in only what is missing rather than
creating a second tree under `automation/`. See the comment block in
`.gitignore` for how tracking is handled at the root.
